Summary

Goal
Make the web runner expose two primary flows: learn good tweets from home+own tweets, and learn good replies from one tweet plus replies.
Source
User requested separate tweet-learning and reply-learning workflows.
Surface
public/index.html, POST /api/run, prompt contract.
Schema
Reuse data/raw and data/digests; add workflow names only.
Guidance
Tweet flow updates tweet-guidance.md; reply flow updates reply-guidance.md.
Open Qs
0.

API contract

POST /api/run
{ "workflow": "tweet-learnings" }

POST /api/run
{ "workflow": "reply-learnings", "tweetUrl": "https://x.com/.../status/..." }

UI layout

  1. Learn good tweets: run from home timeline plus the user's tweets/replies.
  2. Learn good replies: require a tweet URL, scrape original tweet plus replies, and update reply guidance.

Decisions

IDChoice · Rationale
D-001Add new workflow keys without deleting old ones. Existing generated data and buttons can keep working through the API.
D-002Require a URL for reply-learning. Reply quality depends on a specific conversation.
D-003Keep reply guidance separate. Good replies optimize for conversation fit, not standalone hooks.

Tradeoffs

IDPicked over Rejected · Reason
T-001Two workflow buttons over a full queue manager. One run at a time already matches the SDK runner.

Reversibility

R-001 · low. Revert the touched files and delete reply-guidance.md if reply guidance should merge back into tweet guidance.

Definition of done

  • Web app shows the two primary flows.
  • reply-learnings validates a tweet URL and passes it to the agent prompt.
  • Prompt contract tells the agent how to update tweet and reply guidance separately.
  • cd twitter-daily && npm run check passes.
  • POST /api/run smoke rejects reply-learnings without a tweet URL before SDK startup.
  • node --check poaster-app/sandbox-runtime/pi-runner.js && cd poaster-app && npm run test passes.
